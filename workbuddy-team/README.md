# WorkBuddy 交付团

一句话需求进，可验证的功能出。

这个专家团把"探索 → 规格 → 批准 → 实现 → 验收 → 归档"六个阶段拆给五个角色，由主理人串联。你只需要说一次需求，并在规格写完后点一次头。

## 团队

| 角色 | 称呼 | 职责 |
|---|---|---|
| 主理人 | 阿特 Atlas | 编排阶段、派发成员、汇总结果、与你交互 |
| 需求澄清师 | 探路 Scout | 把模糊需求压成最多三个关键问题加一份假设清单 |
| 规格架构师 | 蓝图 Blue | 产出 proposal / specs / design / tasks 四件规格 |
| 全栈工程师 | 锻工 Forge | 按任务清单写代码，完成一条勾一条 |
| 验收工程师 | 验官 Verdict | 跑构建与测试，输出可定位的验收结论 |

## 流程

```
你说一句需求
    │
    ├─ 探路   澄清范围（可跳过，但假设必须写进闸门）
    ├─ 口径   有不可逆选择时一次问完（≤3 个），再写规格
    ├─ 蓝图   按 S/M/L 档位写四件规格
    │
    ├─ 【停】档位 / 已定口径 / 范围 / 非目标 / 任务分解 / 风险
    │        你点头 ← 唯一需要批准的地方
    │
    ├─ 锻工   按文件分批实现，边做边勾（同一文件不拆批）
    ├─ 验官   构建 + 测试
    │    └ 失败 → 带证据回给锻工，最多 3 轮 → 仍不过就问你
    │
    └─ 归档   需求沉淀成长期文档
```

改动规模分三档：S（单文件/单接口/单按钮，场景 ≤20、任务 ≤12、实现 ≤2 批）、M（单端多文件，场景 ≤40、任务 ≤24）、L（跨端/跨模块，超限须说明理由）。小改动不再套大流程。

## 三条硬规则

1. **闸门前不写代码**。规格没写完、你没批准，不会动你的源码。
2. **验收不通过不归档**。构建或测试挂了，变更会停在原地，不会"假装完成"。
3. **进度以文件为准**。中断后回来说"继续"，从第一个没勾选的任务接着做，不会重做已完成的部分。

## 验收的四种结论

| 结论 | 含义 |
|---|---|
| 通过 | 构建与测试都跑通 |
| 仅构建通过 | 构建跑通，但项目没有测试 |
| 失败 | 有命令报错，附带文件与行号 |
| 未验证 | 连构建都跑不起来 |

后两种不会归档；第二种会归档，但报告里会写明"无测试覆盖"。

## 前置条件

只有一个：本机有 Node.js（>= 18）。

包内自带工具 `wbspec`，负责建变更、查状态、校验结构、归档并合并主规格。它只用 Node 标准库，不联网、不装任何依赖，也不需要另行安装 OpenSpec。

目标项目没有 `openspec/` 目录时，主理人会自己跑一次 `wbspec init`。

如果 PATH 里找不到 `wbspec`，用包内路径 `./bin/wbspec` 调用。本机没有 Node 时工具会以退出码 127 结束，流程转为按 `references/protocol/protocol.md` 手工执行——备份与对账单照样不能省。

## 第一次使用

直接用下面的提示词召唤：

> 帮我做一个功能，我只说一句话，你负责把规格、代码、测试、归档都走完。

首次运行会自动识别项目技术栈（语言、框架、构建命令、测试命令），写进该项目的 `openspec/config.yaml`，之后不再重复询问。

## 已知限制

- 工具权限由平台统一分配，成员无法在定义中限制工具；"验官不改代码"靠提示词约束，不是系统级强制。
- 验收的"三轮上限"是提示词逻辑，不是代码逻辑。
- 项目没有测试时，只能验到"构建通过"，不能替代真实测试覆盖。
